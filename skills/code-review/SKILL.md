# SKILL: code-review

Ревьюишь свою ветку до того, как её увидит человек. Пять осей, каждая — один
проход по диффу, а не один проход по пяти вопросам.

## 1. Корректность

* каждый `error` обработан или явно обоснованно проигнорирован;
* граничные случаи: пустая строка, nil-карта, отсутствующий сервис, неизвестная
  сессия;
* идемпотентность: `Up`, `Apply`, `Reset`, `Down` по одному и тому же id
* состояние после ошибки: сессия не осталась «running», если окружение не
  поднялось.

## 2. Читаемость

* функция делает одну вещь и укладывается в ~40 строк;
* комментарий объясняет *почему*, а не *что*; запрещенные комментарии вида
  `// инкремент счётчика`;
* имена говорят о роли: `session`, `project`, `patch`, а не `x`, `data2`;
* в сообщении коммита первая строка <= 50 символов и объясняет причину.

## 3. Архитектура

* зависимости направлены внутрь: адаптеры не знают про манифест, ядро знает про
  оба;
* новый движок = один файл, реализующий `runtime.Adapter`, без правок ядра;
* новая задача = один YAML, без правок ядра;
* нет циклических импортов и нет импорта `internal/adapters/...` из ядра.

## 4. Безопасность

* секреты из манифеста не пишутся в журнал и в ответы API;
* адрес прослушивания по умолчанию loopback;
* пути к файлам состояния не выходят за `Config.StateDir`;
* exec-команды проверки не интерпретируются как строки без необходимости
  (аргументы — отдельные элементы среза).

## 5. Производительность

* нет `time.Sleep` в горячем пути вместо ожидания условия;
* нет опроса в цикле без бюджета времени;
* журнал пишется пачками только если это осознанно (иначе — `Sync` на запись);
* метрики и логи читаются с ограничением (`--tail`), иначе длинная сессия
  раздувает ответ API.

## Порядок перед коммитом

```console
$ gofmt -l .            # пусто
$ go vet ./...          # пусто
$ go test ./...         # зелено
$ git diff --stat       # <= 500 строк кода на ветку
```

Если дифф больше — режь ветку, наследуя следующую от текущей
([git-workflow](git-workflow/SKILL.md)).

# SKILL: spec-first

Применяется в начале любой ветки, на которой появляется новый подсистема или
новый тип данных. Спецификация — [`README.md`](../../README.md), раздел 4.
Скиллы ссылаются друг на друга и на спецификацию, а не дублируют её.

## Когда применять

* перед `feat/manifest-schema`, `feat/interfaces`, `feat/verifier-replay`,
  `feat/content-*` — везде, где появляется новый контракт;
* когда манифест task'а не описывает поведение однозначно;
* когда хочется «добавить ещё одно поле в схему».

## Порядок

1. **Найди якорь в спецификации.** Цитата + раздел. Нет якоря — остановись и
   спроси, а не додумывай.
2. **Выпиши договорённости, которые уже зафиксированы** (имёнa полей, типы
   injector'ов, состав gate'ей). Всё остальное — открытые вопросы.
3. **Задай уточняющие вопросы до кода** (2–5 штук, с вариантами ответа).
   Типовые:
   * уровень задачи — config / code / db / composite?
   * что считается корректным поведением (endpoint, метрика, SQL-факт)?
   * чем distractor отличается от решения (какой артефакт проверяем)?
   * нужен ли fault_chain и какие звенья должны разорваться?
4. **Составь план ветки**: коммиты, объём каждого (<= 500 строк кода), что
   остаётся в проходящем состоянии после каждого коммита. План — в описании
   ветки или в списке задач.
5. **Только потом код.** Если в процессе план изменился — обнови план, а не
   молча расширяй коммит.

## Чек-лист ветки

* [ ] в спецификации есть якорь для каждого нового поля/типа;
* [ ] открытые вопросы заданы и закрыты (или зафиксированы как TODO);
* [ ] план ветки разбит на атомарные коммиты;
* [ ] новые типы данных описаны схемой и тестом на невалидный случай;
* [ ] импорт из спецификации не дублируется в коде — поле читается из манифеста.

## Как проверить скилл

Возьми любую новую задачу каталога (`manifests/*.yaml`) и пройди чек-лист
заново: если хотя бы один пункт не выполняется у существующего манифеста —
либо манифест, либо скилл требуют правки.

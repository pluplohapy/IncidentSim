# SKILL: git-workflow

Правила фиксируются в спецификации, раздел 5. Здесь — как их применять на
практике, без повтора формулировок.

## Ветка

* одна ветка = один логический шаг (`feat/manifest-schema`), а не эпик;
* короткоживущая: живёт от предыдущего коммита этапа до мержа;
* имя начинается с `feat/`, дальше — предмет шага через дефис.

## Stacked branches

Этапы спецификации выстроены цепочкой: каждая следующая ветка наследует
предыдущую, чтобы каждый слой было можно ревьюить и мержать независимо.

```console
$ git switch main
$ git switch -c feat/manifest-schema        # от мейна
$ git switch -c feat/interfaces             # от manifest-schema, не от мейна
```

Правило: новая ветка создаётся **от tip'а предыдущей**, иначе стопка ломается и
приходится делать rebase-каскад.

## Коммит

* атомарный: один коммит = одна подзадача;
* сообщение объясняет **почему**, первая строка <= 50 символов, императив;
* перед коммитом: `make check` (fmt + vet + test);
* если коммит трогает больше 500 строк кода (без сгенерированных файлов,
  lock-файлов и форматирования) — дели на два и наследуй ветку дальше.

```console
$ git commit -m "define runtime interface" -m "Контракт, от которого зависят
адаптеры, инъекторы и верификатор; реализаций здесь нет намеренно."
```

## Чего не делать

* не открывать PR за автора: автор собирает PR сам из готовых веток;
* не делать `git push --force` в `main` и в уже отправленные ветки;
* не смешивать несвязанные изменения в одной ветке;
* не оставлять коммит, ломающий сборку или тесты.

## Чек-лист

* [ ] ветка названа по шагу, а не по эпику;
* [ ] ветка создана от tip'а предыдущей;
* [ ] каждый коммит оставляет код зелёным;
* [ ] первая строка сообщения <= 50 символов;
* [ ] объём ветки в пределах лимита или разделение обосновано.

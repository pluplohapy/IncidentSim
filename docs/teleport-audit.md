# Аудит сессий через Teleport (опционально)

Экспериментальный адаптер записи сессий. Он вне основного пути MVP: ядро не
зависит от него, отсутствующий или сломанный бэкенд — это предупреждение в
журнале, а не упавшая сессия. Реальный кластер Teleport этим репозиторием не
проверялся, поэтому endpoint и payload нельзя считать подтвержденной
интеграцией.

## Что он делает

Считанная запись (`SessionRecord`) содержит id сессии, id задачи, время начала
и конца. В MVP в записи нет терминального вывода участника: в compose-движке
некуда его прикреплять, а в Firecracker ввод участника идёт через vsock-агент,
и его запись — отдельная задача. Интерфейс оставлен под неё:

```go
type AuditRecorder interface {
	Record(ctx context.Context, record SessionRecord) error
	Name() string
}
```

## Как включить

В [`incidentsim.yaml`](../incidentsim.yaml):

```yaml
teleport:
  enabled: true
  endpoint: teleport.example.com:3080
```

и запустить ядро с непустым `join token` в окружении:

```console
$ INCIDENTSIM_TELEPORT_TOKEN=... bin/incidentsim serve
```

При `enabled: false` (значение по умолчанию) работает `teleport-stub`: записи
хранятся в памяти процесса и не выгружаются никуда. Это осознанное поведение —
включить аудит должны явно, а не потому что эндпоинт оказался прописан.

## Границы

* адаптер не трогает поведение задач, проверки и шлюзы;
* запись происходит в `Stop`, то есть по завершении сессии: живая сессия не
  уходит в настроенный экспериментальный HTTP endpoint;
* сеть до Teleport нужна хосту, где работает ядро. Внутри microVM сети нет —
  и это by design: участник не достаёт интернет из тренажёра.

## Что не сделано в MVP

* нет записи потока терминала (compose-движок не даёт ptc участника);
* нет группировки записей по участникам — идентификация вне тренажёра;
* нет retry для загрузки: неудачная загрузка пишется в журнал сессии как
  `audit could not record the session`.
